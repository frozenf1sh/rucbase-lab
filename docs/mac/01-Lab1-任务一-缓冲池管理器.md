## 0. 大局观：为什么要有缓冲池

DBMS 的所有"持久数据"都在磁盘上，按固定大小（本工程 `PAGE_SIZE = 4 KiB`）切成"页"线性存储。但磁盘 I/O 比 RAM 慢 5～6 个数量级，每次查询都直接读盘是不可接受的。**缓冲池**就是 DBMS 在内存里维护的一块固定大小（`pool_size` 个 frame）的"近缓存"，把热点页面留在内存里反复使用，并在合适时机批量写回磁盘。

整个存储模块呈现一个清晰的三层结构：

```
┌──────────────────────────────────────────────────────────────┐
│  上层调用方（执行器 / 索引 / 记录管理器）                      │
│         fetch_page / new_page / unpin_page / flush_page       │
├───────────────────── BufferPoolManager ──────────────────────┤
│   pages_[]    page_table_    free_list_                       │
│   replacer_ ←→ LRU 替换策略（任务 1.2）                        │
├──────────────────── DiskManager（任务 1.1）──────────────────┤
│   read_page / write_page / open / close / create / destroy    │
├──────────────────────── 操作系统 / 磁盘 ──────────────────────┤
│            open(2) / read(2) / write(2) / lseek(2)            │
└──────────────────────────────────────────────────────────────┘
```

三个子任务恰好覆盖了"如何把数据搬上搬下、如何决定谁来腾位、如何在两者之上提供透明的 API"。

> **Q0：缓冲池里的"页"和磁盘上的"页"是不是同一份数据？**
> A：物理上不是，是缓存关系。每个 frame 持有一份磁盘页内容的拷贝。三种状态：(1) 与磁盘一致——干净；(2) 内存比磁盘新——脏，下次 victim/flush 时必须先写回；(3) frame 还没装载任何页——挂在 `free_list_` 中。

## 1. 任务 1.1 · DiskManager（10 分）

### 1.1.1 职责与接口

`DiskManager` 是 DBMS 与文件系统之间唯一的桥梁。它把 POSIX 文件 API（`open / read / write / lseek / unlink`）封装成「按页」的接口。本任务实现 6 个函数：

| 函数 | 作用 | 关键 syscall |
|---|---|---|
| `write_page(fd, page_no, buf, n)` | 把 buf 的 n 字节写到文件 fd 的第 page_no 页起始处 | `lseek + write` |
| `read_page(fd, page_no, buf, n)` | 从文件 fd 的第 page_no 页起始处读 n 字节到 buf | `lseek + read` |
| `create_file(path)` | 创建新文件，已存在则抛 `FileExistsError` | `open(O_CREAT｜O_EXCL)` |
| `destroy_file(path)` | 删除文件，未关闭则抛 `FileNotClosedError` | `unlink` |
| `open_file(path)`  | 打开（不可重复打开），返回 fd | `open(O_RDWR)` |
| `close_file(fd)`   | 关闭，并维护 `path↔fd` 双向表 | `close` |

> 此外还有 `is_file / is_dir / allocate_page / read_log / write_log` 等已经给好的辅助函数，本任务**不需**改。

### 1.1.2 关键实现要点

#### (a) `write_page` / `read_page`：按页定位

任意一页在文件中的字节偏移就是 `page_no * PAGE_SIZE`。所以伪代码就是

```cpp
lseek(fd, off_t(page_no) * PAGE_SIZE, SEEK_SET);
ssize_t n = write(fd, buf, num_bytes);   // 或 read
if (n != num_bytes) throw InternalError(...);
```

注意三件事：
1. `off_t(page_no) * PAGE_SIZE` 必须先转 `off_t` 再乘，否则当 `page_no` 较大、`PAGE_SIZE` 还是 `int` 时容易 32-bit 溢出。
2. `read` / `write` 完成的字节数小于 `num_bytes` 视为错误：原子写不保证（被信号中断、磁盘满都会发生），但本工程把上层语义定义为"全有或全无"。
3. 返回 -1 也走 `n != num_bytes` 这条路径，所以一个判断就够了。

#### (b) `create_file`：用 `O_CREAT | O_EXCL` 解决 TOCTOU

天然的写法是「先 `is_file` 判断不存在，再 `open(O_CREAT)`」。但这两步之间有时间窗，多进程并发时会出竞态。`O_EXCL` 让内核保证"文件已存在则失败"，是 POSIX 推荐做法。
此外文件权限给 `0600`（仅当前用户读写），最安全。
开完文件立刻 `close`：本函数语义是"创建"，不持有 fd；调用方将通过 `open_file` 再打开一次。

#### (c) `open_file`：维护双向表

`DiskManager` 持有两张表：

```cpp
std::unordered_map<std::string, int> path2fd_;
std::unordered_map<int, std::string> fd2path_;
```

它们的作用：
1. 让 `destroy_file` 能在删除前判断"文件是否还处于打开态"；
2. 让其他模块通过 `get_file_name(fd)` 反查路径（恢复 / 日志会用）。
3. 实现"同一路径不重复打开"的语义。

`open_file` 必须同时插入这两张表；`close_file` 也必须同时清理两张表，否则就会出现"文件已关但表里还在"的不一致。

#### (d) 异常体系

整个工程沿用 `errors.h` 里定义的 `RMDBError` 派生类：

| 异常 | 含义 |
|---|---|
| `FileNotFoundError` | 文件不存在 |
| `FileExistsError`   | 文件已存在 |
| `FileNotOpenError`  | 操作了未打开的 fd |
| `FileNotClosedError`| 试图删除一个仍处于打开状态的文件 |
| `UnixError`         | POSIX syscall 失败（自动读 errno）|
| `InternalError`     | 业务约束被破坏 |

> **Q1.1：为什么读写页面要先 `lseek`？不是有 `pread/pwrite` 吗？**
> A：`pread / pwrite` 是更优的选择（线程安全、避免 fd 偏移竞争）。这里沿用 `lseek+read/write` 是为了保持与教学文档/上游 Linux 实现一致；在多线程场景下我们用 `BufferPoolManager` 的 `latch_` 把这一对调用串行化，所以仍然安全。

> **Q1.2：`create_file` 为什么不能写成"先 `is_file` 再 `open(O_CREAT)`"？**
> A：(1) 即使没有 `O_EXCL`，`O_CREAT` 在文件已存在时也不会报错，会直接返回原文件 fd——和"重复创建则抛异常"的语义不符。(2) 即使先做 `is_file`，从判断到 `open` 之间存在 race（TOCTOU）。`O_CREAT｜O_EXCL` 让内核在原子层面拒绝已存在的文件。

> **Q1.3：`destroy_file` 为什么要拒绝删未关闭的文件？POSIX 不是允许 unlink 后照常 read/write 吗？**
> A：POSIX 确实允许，文件 inode 会等所有 fd 关闭后才回收。但在 DBMS 语义里，"文件已删除"应该意味着所有客户端立刻不能再访问；让 `destroy_file` 抛 `FileNotClosedError` 可以把这种"半删除"状态扼杀在调用层，避免上层逻辑的误用。

## 2. 任务 1.2 · LRUReplacer（20 分）

### 2.1 角色与接口

`LRUReplacer` 是一个**只在 `pin_count == 0` 的 frame 集合上工作**的"可淘汰候选池"。`BufferPoolManager` 在以下时机调用它：

| 时机 | 调用 |
|---|---|
| `unpin_page` 把 pin_count 由 1 减到 0 | `replacer_->unpin(frame_id)` —— 把 frame 加入候选 |
| `fetch_page / new_page` 命中或新建后立刻 pin 该 frame | `replacer_->pin(frame_id)` —— 从候选中移除 |
| `find_victim_page` 找不到 free frame | `replacer_->victim(&frame_id)` —— 选一个挤掉 |

接口规约：

```cpp
bool victim(frame_id_t *frame_id);   // 选一个最 LRU 的 frame，返回；空集合时返回 false
void pin(frame_id_t frame_id);       // 从候选集合移除（不在则 no-op）
void unpin(frame_id_t frame_id);     // 加入候选集合（已在则 no-op）
size_t Size();                       // 当前候选数量
```

### 2.2 数据结构选择：list + hash 经典组合

```cpp
std::list<frame_id_t>                                       LRUlist_;
std::unordered_map<frame_id_t, std::list<...>::iterator>    LRUhash_;
```

之所以用这套：

| 操作 | 朴素实现 | list+hash |
|---|---|---|
| `unpin(x)`：插入「最新」位置 | list O(1)，但去重需 O(n) | **O(1)**（hash 查重）|
| `pin(x)`：从中间任意位置删除 | array O(n) | **O(1)**（hash 拿迭代器）|
| `victim()`：取「最旧」 | list O(1) | **O(1)** |

list 的迭代器在 `splice / erase` 之外都保持稳定，可以放心存进 hash。

约定：**list 头 = 最近被 unpin（最不该淘汰），list 尾 = 最久未被 unpin（最该淘汰）**。

### 2.3 关键不变式

1. `LRUhash_.size() == LRUlist_.size()`，且 `LRUhash_[id]` 必须指向 `LRUlist_` 中存放 `id` 的那个节点。
2. `LRUlist_.size() <= max_size_`。
3. 三个 public 方法各自整段持有 `latch_`，所以 hash 与 list 的更新对外原子。

### 2.4 行为细节（容易踩坑的地方）

#### (a) `unpin` 必须**幂等**

测试 `SimpleTest` 里有这样一段：

```cpp
lru_replacer.unpin(1);  // 第一次
... // unpin 2..6
lru_replacer.unpin(1);  // 第二次！
EXPECT_EQ(6, lru_replacer.Size());        // size 仍是 6，没多
victim → 1, victim → 2, victim → 3        // 1 仍然是最早被 unpin 的
```

所以语义是：如果 frame 已在候选集合中，**不要把它移到首部，也不要重复插入**。这呼应了上层 `BufferPoolManager` 的设计：`unpin` 只在 `pin_count` 由 1 减到 0 的瞬间被 buffer pool 调用一次，多次调用应当退化为 no-op。

#### (b) `pin` / `unpin` 的对称性

`pin` 找不到就 no-op；`unpin` 找到了也 no-op。这两条规则联合保证了 `BufferPoolManager` 在并发场景下的高鲁棒性：即便上层逻辑短暂"颠倒一拍"（先 unpin 再 pin / 先 pin 再 unpin），replacer 内部状态依然合法。

#### (c) 容量保护

理论上 `BufferPoolManager` 会保证候选数量不超过 `pool_size`，但实现时仍要防御性地检查：

```cpp
if (LRUlist_.size() >= max_size_) return;
```

避免上层逻辑出 bug 时 replacer 内存无限增长。

> **Q2.1：为什么不直接用 `std::unordered_set<frame_id_t>` 配合一个全局时间戳？**
> A：(1) 时间戳方案 `victim` 必须 O(n) 扫所有元素找最小，性能差；(2) 时间戳还要处理回卷；(3) list+hash 三个操作都是 O(1)，常数也很小。学术界标准实现就是这套。

> **Q2.2：你这里的"最近被使用"等于"最近被 unpin"，这合理吗？我把一个页面 fetch + 用 + unpin，难道使用时间不应该是 fetch 时刻？**
> A：在 BufferPoolManager 里，**页面正在被使用时它的 frame 是 pinned 状态**，根本不在 replacer 的候选集合里——所以"使用中"根本谈不上 LRU 排序。只有 `unpin` 那一刻 frame 才回到候选池，把"unpin 时刻"作为时间戳是恰当的；而且这是工业实现（包括 BusTub）的通行做法。

> **Q2.3：并发下你怎么保证 victim 选出来的 frame 不会同时被另一个线程 pin 走？**
> A：`victim` 内部持锁；返回的 frame_id 已经从 LRUlist_/LRUhash_ 中移除，对 replacer 内部不再可见。后续 `BufferPoolManager` 会在自己的 `latch_` 保护下立刻把这个 frame 装上新页并 `replacer_->pin`（其实只是再 no-op 一次，因为已经不在候选池），不会出现"两个线程同时拿到同一个 frame"的情况。

> **Q2.4：为什么 `Size()` 也要加锁？**
> A：list 的 `size()` 是 O(1) 但读 `_M_size_` 字段的原子性并无保证；并发 unpin 的时候可能读到中间值。加锁是为了观察一个逻辑一致的快照。

## 3. 任务 1.3 · BufferPoolManager（40 分）

### 3.1 数据结构地图

```cpp
size_t                                       pool_size_;
Page                                         pages_[pool_size_];   // frame 数组
std::unordered_map<PageId, frame_id_t,
                   PageIdHash>               page_table_;          // 反向索引
std::list<frame_id_t>                        free_list_;           // 干净空帧
DiskManager*                                 disk_manager_;
Replacer*                                    replacer_;            // 任务 1.2
std::mutex                                   latch_;               // 整池大锁
```

每个 frame 上的 `Page` 自带：`PageId id_`、`char data_[PAGE_SIZE]`、`bool is_dirty_`、`int pin_count_`。

### 3.2 核心不变式（实现 / Debug 时反复对照）

| 不变式 | 含义 |
|---|---|
| **I1** | 任一 frame 要么属于 `free_list_`，要么有效绑定到一个 `PageId` 并存于 `page_table_` |
| **I2** | `free_list_` 中的 frame 不在 `replacer_` 候选集中 |
| **I3** | `replacer_` 候选集 ⊆ "有效绑定 PageId 且 pin_count==0" 的 frame |
| **I4** | dirty frame 在被 victim 出局前必须先 `write_page` |
| **I5** | `page->id_ == INVALID_PAGE_ID` ⇔ 该 frame 当前空闲（在 free_list 中） |

### 3.3 设计的核心：`update_page` 与 `find_victim_page` 两个内部辅助

把"找 frame"和"把 frame 切换到新身份"两步通用化，能让上层 6 个 public 方法的代码量大幅缩短，也便于日后调优。

#### `find_victim_page(frame_id_t* out)`

```text
1. free_list_ 非空：取出一个，返回 true
2. 否则：调用 replacer_->victim(out)
3. 都失败 → 返回 false（上层应当返回 nullptr）
```

约束：**调用方必须已持 latch_**，本函数不再二次加锁，否则与外层重复加 `std::mutex` 导致死锁。

#### `update_page(page, new_pid, new_frame)`

这是把一个 frame 从"承载旧页"过渡到"承载新页"的统一原子动作：

```text
1. 若 page->is_dirty_：用 page->id_（旧 PageId）写回磁盘，is_dirty_ = false
2. 若 page->id_.page_no != INVALID：从 page_table_ 中 erase 旧 PageId
3. 若 new_pid.page_no != INVALID：page_table_[new_pid] = new_frame
4. page->reset_memory();  page->id_ = new_pid;
```

第 3 步那一行的 `if` 至关重要——`delete_page` 会传 `new_pid={fd, INVALID}`，表示"这个 frame 接下来要还给 free_list_，不要往 page_table_ 里塞 INVALID 项"。

### 3.4 六个 public 方法

每个方法第一行都是 `std::scoped_lock lock{latch_};`，全程持锁，保证操作 atomic。

#### `fetch_page(page_id) -> Page*`

```text
if page_table_ 命中：
    pin_count_++; replacer_->pin(frame); return &pages_[frame]
else:
    if !find_victim_page(&frame): return nullptr
    update_page(page, page_id, frame)              // 写回脏 + 切换映射 + reset
    disk_manager_->read_page(page_id.fd, page_id.page_no, page->data_, PAGE_SIZE)
    page->pin_count_ = 1; replacer_->pin(frame)
    return page
```

注意 `read_page` 必须**在 `update_page` 之后**——`reset_memory` 会清零 `data_`，先 read 后 reset 等于把读上来的内容洗掉。

#### `unpin_page(page_id, is_dirty) -> bool`

```text
miss → false
pin_count_ <= 0 → false
pin_count_--
if pin_count_ == 0: replacer_->unpin(frame)
if is_dirty: page->is_dirty_ = true   // 单调升级，不能由 false 覆盖 true
return true
```

**经典坑**：`page->is_dirty_ = is_dirty;` 是错的。例：线程 A `unpin(true)`（写过），紧接着线程 B `unpin(false)`（只读），如果直接覆盖会丢脏，磁盘永远不会刷。正确做法是 *只能从 false 升到 true*。

#### `flush_page(page_id) -> bool`

```text
miss → false
write_page(...);  is_dirty_ = false
return true
```

题目要求"无论是否脏都强制刷"，这里照做。

#### `new_page(page_id*) -> Page*`

```text
if !find_victim_page(&frame): return nullptr
new_pid.fd = page_id->fd
new_pid.page_no = disk_manager_->allocate_page(new_pid.fd)
update_page(page, new_pid, frame)
page->pin_count_ = 1; replacer_->pin(frame)
*page_id = new_pid; return page
```

为什么不需要立刻 `write_page`？因为 `reset_memory` 把 data_ 清零后，新页只会等"下次 victim 出局"或"显式 flush"时才需要落盘；在那之前任何 fetch 都会命中缓冲池。这避免了不必要的 I/O。

#### `delete_page(page_id) -> bool`

```text
miss → true   // 不在池中视为成功（题目语义）
pin_count_ != 0 → false
update_page(page, {fd, INVALID_PAGE_ID}, frame)   // 写回脏 + erase 映射 + reset
free_list_.push_back(frame)
replacer_->pin(frame)                              // 把它从 LRU 候选里摘掉
return true
```

最后那行 `replacer_->pin(frame)` 是**必要**的：被删的页在删除前 `pin_count_` 是 0，意味着此 frame 仍在 replacer 候选池里。如果不主动 pin 出来，下一次 `find_victim_page` 走 free_list_ 取了它，同时 replacer 也可能选到它，造成同一个 frame 被发放两次。

#### `flush_all_pages(fd)`

```text
foreach (pid, frame) in page_table_:
    if pid.fd == fd:
        write_page(...)
        is_dirty_ = false
```

不要在循环里调用 `flush_page`——`std::mutex` 不可重入，会死锁。

### 3.5 并发模型

整池一把 `std::mutex` 锁，所有 public 方法整段持有。这种"大锁"实现简单、易证明正确性，已经能通过所有并发测试（`ConcurrencyTest` 5 线程 × 50 轮）。
工业级实现会进一步做：每个 frame 各持 reader-writer latch、page_table_ 用并发 hashmap、replacer 用 sharded LRU 等。题目允许且鼓励这类优化（"学生可以考虑这些函数之间的并发执行逻辑，加以改进"），但本实现以**正确性优先**。

> **Q3.1：`fetch_page` 命中时为什么也要 `replacer_->pin(frame)`？这个 frame 此时在不在 replacer 候选集里？**
> A：考虑这种场景：线程 A 持有 page_id 调 `unpin(false)`，pin_count 变 0，frame 进入 replacer 候选；紧接着线程 B 调 `fetch_page(page_id)` 命中，pin_count++。此时这个 frame 仍在 replacer 候选集里！如果不立刻 `replacer_->pin(frame)` 把它捞出来，后续别的 fetch 在做 victim 时可能选中它，把"正在被 B 使用的页"挤掉。LRUReplacer 的 `pin` 在"不在候选"时是 no-op，所以这一行无论命中与否都是安全且必要的。

> **Q3.2：你的 `update_page` 把 reset_memory 放在写回脏之后，看起来很合理。但如果 reset_memory 在 update_page 内部、`fetch_page` 又依赖 reset_memory 之后再 read_page，会不会浪费一次清零？**
> A：会，确实多了一次 `memset(PAGE_SIZE)`。但这次 memset 是 SIMD 优化下纯内存操作，约 1 μs；相比 `read_page` 的磁盘 I/O（毫秒级）可忽略不计。换来的好处是 `update_page` 的语义高度统一：调用方不必再担心 frame 上的旧数据残留。

> **Q3.3：`new_page` 之后没有 `write_page`，那如果数据库进程崩溃了，新页面是不是就丢了？**
> A：对。这恰好就是为什么需要"WAL 日志 + checkpoint"机制——后续 Lab4 的内容。当前 buffer pool 层只承诺"在干净退出 / 显式 flush 时数据落盘"。新页面若崩溃前没 flush 过，磁盘上的 page_no 范围还在，只是内容是任意旧字节；上层在恢复时会通过 WAL 重做来补全。

> **Q3.4：`unpin_page` 里 `if pin_count_ <= 0 return false`，什么情况下会出现 pin_count 已经是 0 还来 unpin？**
> A：(1) 上层 bug：fetch 一次 unpin 两次；(2) 错误的 page_id（传了一个其实没 fetch 的页）。这条 false 是健壮性兜底——不应该 abort，让上层有机会感知到。

> **Q3.5：你为什么用一把大锁，而不是更细粒度的锁？这不会成为多核扩展性的瓶颈吗？**
> A：(1) 教学项目，正确性优先于扩展性；(2) 当前测试压力 5 线程 × 50 轮 879ms 已经可以跑通；(3) 细粒度方案要解决的难点是"page_table_ 修改 + replacer 操作 + Page 字段修改"三者的原子性，常见做法有：(a) page_table_ 用并发 hashmap + per-frame latch；(b) RCU 风格只读零锁，写时拷贝。这些可作为后续优化方向。

> **Q3.6：你 delete_page 末尾调用 `replacer_->pin(frame)` 把它从候选池摘掉，但这个 frame 现在已经在 free_list 里了，replacer_ 知道这一点吗？**
> A：replacer_ 只跟踪"我加进来的 frame"，它不知道 free_list 的存在。`pin` 的语义是"从我的候选集合中移除"，移除后不论它接下来去哪都跟我无关。所以这行 pin 完成的是"把 frame 从候选池移除"这件唯一的事，正好满足我们维护不变式 I2 的需求。

## 5. 现场答辩"必背速查表"

```
┌──────────────────────────────────────────────────────────────┐
│  缓冲池三大数据结构                                            │
│   pages_[i]      —— frame 数组，i 即 frame_id                 │
│   page_table_    —— PageId -> frame_id  (映射)                │
│   free_list_     —— 没装载任何页的 frame_id 列表               │
│   replacer_      —— 跟踪 pin_count==0 的"可淘汰"集合           │
├──────────────────────────────────────────────────────────────┤
│  LRU 三个动作                                                  │
│   unpin(x)    把 x 加到链表头（已存在则 no-op）                │
│   pin(x)      把 x 从链表移除（不存在则 no-op）                │
│   victim()    弹出链表尾                                       │
├──────────────────────────────────────────────────────────────┤
│  fetch_page 五步                                               │
│   1. 命中？pin_count_++; replacer.pin; 返回                    │
│   2. find_victim_page                                          │
│   3. update_page（脏写回 + 改映射 + reset）                    │
│   4. read_page                                                 │
│   5. pin_count_=1; replacer.pin                                │
├──────────────────────────────────────────────────────────────┤
│  unpin_page 关键三句                                           │
│   1. 找不到 / pin_count<=0 → false                             │
│   2. pin_count_--；==0 时 replacer.unpin                       │
│   3. is_dirty 只能升级 (false→true)，不能覆盖                  │
├──────────────────────────────────────────────────────────────┤
│  脏页回写时机                                                  │
│   victim 出局前（update_page 第 1 步）                         │
│   显式 flush_page / flush_all_pages                            │
│   delete_page（也走 update_page）                              │
└──────────────────────────────────────────────────────────────┘
```
