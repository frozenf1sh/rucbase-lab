## 0. 大局观：记录管理器是 DBMS 的"行存引擎"

任务一的缓冲池管理器解决了「磁盘页 ↔ 内存帧」之间的搬运问题，但上层并不直接操作"页"——它操作"行"（一条 SQL 元组）。**记录管理器**的职责就是把"逻辑上的一条记录"映射到"某个页的某个槽位"，并提供 `get / insert / delete / update / scan` 5 个统一接口。

```
┌──────────────────────────────────────────────────────────────┐
│  执行器 (Lab3)：拿到 SQL 计划，对元组执行 select/insert/...    │
├──────────────────────────────────────────────────────────────┤
│  RmManager        创建/打开/关闭/删除一个表数据文件            │
│  RmFileHandle     单个表文件的"按记录"接口（任务 2.1）          │
│  RmScan           顺序扫描该文件的所有记录（任务 2.2）          │
│  RmPageHandle     单个 record-data 页的内部视图（已给）        │
├──────────────────────── BufferPoolManager (任务一) ──────────│
└──────────────────────────────────────────────────────────────┘
```

本任务实现的代码全部位于：
- `src/record/rm_file_handle.cpp` — 6 个核心方法 + 2 个辅助方法
- `src/record/rm_scan.cpp` — 3 个迭代器方法

## 1. 关键概念：定长记录的"段式页面"布局

### 1.1 为什么定长

本工程**只支持定长字段**，所以一条记录的字节数 `record_size` 在表创建时就被冻结。这极大简化了：
- 寻址：第 `slot_no` 个槽的偏移恒为 `slot_no * record_size`；
- 元数据：每页 `num_records_per_page` 是个常数；
- 删除/插入：原地置位即可，不需要做"压缩"。

变长记录会引入"槽目录 (slot directory)"和"页内压缩"等复杂机制，留给后续课程。

### 1.2 单页布局

```
                     PAGE_SIZE = 4096 字节
┌─────┬────────────┬───────────────────┬─────────────────────────────────┐
│ LSN │ RmPageHdr  │      bitmap       │            slots[]              │
│ 4 B │ 8 B (实际) │  bitmap_size 字节 │  num_records_per_page × record_size │
└─────┴────────────┴───────────────────┴─────────────────────────────────┘
  ↑
  Page::OFFSET_LSN = 0
              ↑
              Page::OFFSET_PAGE_HDR = 4
```

注意三段的边界都是在 `RmPageHandle` 构造里算好的：

```cpp
page_hdr = page->data + 4                                  // 4 字节 LSN 之后
bitmap   = page->data + 4 + sizeof(RmPageHdr)              // pageHdr 之后
slots    = bitmap + file_hdr->bitmap_size                  // bitmap 之后
```

`RmPageHdr` 是：
```cpp
struct RmPageHdr {
    int next_free_page_no;  // 同一表里下一个未满页的 page_no（链表后继），尾节点 = -1
    int num_records;        // 当前已用 slot 数
};
```

容量上限怎么定？`RmManager::create_file` 里有公式：
```
num_records_per_page = (8*(PAGE_SIZE-1-sizeof(RmFileHdr)) + 1) / (1 + record_size*8)
bitmap_size          = (num_records_per_page + 7) / 8
```
本质上是在解 `sizeof(hdr) + bitmap_size + n*record_size <= PAGE_SIZE`，让 n 最大。

### 1.3 bitmap 的位序

`bitmap.h` 的实现里：
```cpp
get_bit(pos) = BITMAP_HIGHEST_BIT (=0x80) >> (pos % 8)
```
意味着 **slot 0 在字节内是最高位（0x80）**，slot 7 在最低位（0x01）。和直觉的"低位在前"相反，但只要全程用 `Bitmap::set/reset/is_set/next_bit` 就不会出错。

### 1.4 "未满页面单链表"

| 字段 | 含义 |
|---|---|
| `file_hdr_.first_free_page_no` | 链表头页号（链空时 = `RM_NO_PAGE` = -1）|
| 每个未满页 `page_hdr->next_free_page_no` | 链表后继；尾节点 = -1 |

这条链表是 `insert_record` 能 O(1) 找到空位页的关键。如果没有它，每次 insert 都得线性扫所有 page，O(n) 开销。

不变式：**一个页面在链表中 ⇔ 它当前未满**。所有 4 个写路径（insert / 重做 insert / delete / new page）都要负责维护这个不变式。

> **Q1.1：为什么不用"位图描述哪些页是未满的"，而是用单链表？**
> A：(1) 表可能有亿级页面，位图也得 100MB 量级，要常驻；(2) 单链表是"密度感知"的——只追踪未满的少数页面，空间随未满页数成正比；(3) 头插实现下，链表自然有"近期被释放的页优先复用"的局部性，命中缓冲池概率高。

> **Q1.2：链表如果中间断了（例如某个未满页没被插入链表）会怎样？**
> A：表现为"明明文件里有空位，但 insert_record 一直创建新页面，让文件越变越大"。这是教学项目最常见的 bug，调试时第一反应应当对照不变式 I2（链表只串未满页），手工 dump file_hdr 与每页的 page_hdr。

## 2. 任务 2.1 · RmFileHandle（含 6 个方法）

### 2.1.1 fetch / unpin 责任划分

`fetch_page_handle` 调用 `BufferPoolManager::fetch_page` 拿到 `Page*`，并 **pin 了该 frame**。本工程的约定（也被注释 `pin the page, remember to unpin it outside!` 强调）：

> **谁 fetch，谁负责 unpin。**

理由：返回的 `RmPageHandle` 内部的 `page_hdr / bitmap / slots` 三个指针都直接指向 `page->data_`。一旦该 frame 被 victim 出局，这些指针立刻悬空。`RmFileHandle` 在每个写/读路径里都明确知道"什么时候不再需要这页"，正适合在那里 unpin。

我把每条路径的 `unpin(is_dirty)` 表列出来，便于答辩对照：

| 方法 | 路径 | unpin 时机 | is_dirty |
|---|---|---|---|
| `get_record`        | bitmap 命中 | return 前 | **false** |
| `get_record`        | bitmap miss → 抛异常 | 抛之前 | false |
| `insert_record`     | 写完 slot/bitmap/page_hdr | return 前 | **true** |
| `insert_record(rid,buf)` | 重做命中 | return 前 | true |
| `insert_record(rid,buf)` | 重做 miss（已存在） | return 前 | false |
| `delete_record`     | 真的删除了 | return 前 | true |
| `delete_record`     | 重复删除（bitmap 已 0）| return 前 | false |
| `update_record`     | 命中 | return 前 | true |
| `update_record`     | miss → 抛异常 | 抛之前 | false |
| `RmScan::next`      | 每翻一页 | 翻页时立即 | false |

**"is_dirty 必须如实标"** 是缓冲池正确回写的前提：错标 false → 数据丢；错标 true → 多一次磁盘写但不影响正确性。两害相权，宁可"误标 true"。

### 2.1.2 `get_record(rid, ctx)`

```cpp
RmPageHandle h = fetch_page_handle(rid.page_no);
if (!Bitmap::is_set(h.bitmap, rid.slot_no)) { unpin(false); throw RecordNotFoundError; }
auto rec = std::make_unique<RmRecord>(record_size);
memcpy(rec->data, h.get_slot(rid.slot_no), record_size);
unpin(false);
return rec;
```

要点：
1. 一定要 **检查 bitmap**！传入 rid 可能是过期游标 / 用户错误 / 重做日志里的"已被删 rid"。直接读 slot 字节会读到任意脏字节而不是抛错。
2. **拷贝**到独立的 `RmRecord` —— 上层后续会 `unpin` / 缓冲池可能 victim，原 `slot` 内容不可信。

### 2.1.3 `insert_record(buf, ctx) -> Rid`

```cpp
RmPageHandle h = create_page_handle();                         // ① 取/造 一个未满页
int slot = Bitmap::first_bit(false, h.bitmap, n_per_page);     // ② 第一个 0 位即空位
memcpy(h.get_slot(slot), buf, record_size);                    // ③ 写记录
Bitmap::set(h.bitmap, slot);                                   // ④ 占位
h.page_hdr->num_records++;
if (h.page_hdr->num_records == n_per_page) {                   // ⑤ 如果插满了
    file_hdr_.first_free_page_no = h.page_hdr->next_free_page_no;  //   把它从链头摘掉
}
unpin(true);
return Rid{page_no, slot};
```

为什么"如果插满了，被摘掉的一定是链头"？因为 `create_page_handle` 优先返回 `first_free_page_no` 指向的那页；新建页时也会插入链头。所以"我们刚刚写过的那页 = 当前链头"恒成立。

### 2.1.4 `insert_record(rid, buf)` —— 重做用

不被任务一/二的测试调用，但 `RmFileHandle::insert_record` 接口有重载，且 Lab4 的恢复 (redo) 会用到。关键差异：必须把记录恰好写到 rid 指定的位置，不能挑别处。

实现要点（详见代码注释）：
- 幂等：如果 `bitmap[slot] == 1`（已有内容）则 no-op；
- 如果插完正好满，需要从 free 链中**精确摘除**该页（可能不在链头，所以做一次线性扫描）。

### 2.1.5 `delete_record(rid, ctx)`

```cpp
RmPageHandle h = fetch_page_handle(rid.page_no);
if (!Bitmap::is_set(h.bitmap, rid.slot_no)) { unpin(false); return; }   // 幂等
bool was_full = (h.page_hdr->num_records == n_per_page);                // 关键：删之前先记下
Bitmap::reset(h.bitmap, rid.slot_no);
h.page_hdr->num_records--;
if (was_full) release_page_handle(h);                                   // 满 → 未满，挂回链
unpin(true);
```

**经典坑：`was_full` 必须在 `num_records--` 之前求值！** 否则永远拿不到"满"的状态，free 链就再也接不上这页，导致后续 insert 全部新建页面，文件无限膨胀。

### 2.1.6 `update_record(rid, buf, ctx)`

定长更新极简：fetch → memcpy → unpin(true)。
注意还是要 `is_set` 校验，否则"更新一条已删除记录"会静默成功，污染数据。

### 2.1.7 `fetch_page_handle(page_no)`（辅助）

```cpp
if (page_no <= 0 || page_no >= file_hdr_.num_pages) throw PageNotExistError;
Page* p = bpm->fetch_page({fd_, page_no});
if (p == nullptr) throw PageNotExistError;
return RmPageHandle(&file_hdr_, p);
```

为什么 `page_no <= 0` 也要拒绝？`page_no = 0` 是文件头页，**不通过缓冲池访问**（`RmManager::close_file` 直接 `disk_manager->write_page`）；`page_no < 0` 显然非法。

### 2.1.8 `create_new_page_handle`（辅助）

```cpp
PageId pid{fd_, INVALID_PAGE_ID};
Page* p = bpm->new_page(&pid);                                  // ① 申请新 frame + 自增 page_no
RmPageHandle h(&file_hdr_, p);
h.page_hdr->num_records       = 0;                              // ② 显式初始化页头
h.page_hdr->next_free_page_no = RM_NO_PAGE;
Bitmap::init(h.bitmap, file_hdr_.bitmap_size);                  // ③ bitmap 全 0
file_hdr_.num_pages++;                                          // ④ 维护 file_hdr
h.page_hdr->next_free_page_no = file_hdr_.first_free_page_no;   // ⑤ 头插到 free 链
file_hdr_.first_free_page_no  = pid.page_no;
return h;
```

第 ② 步 `next_free_page_no = RM_NO_PAGE` 而不是 0：BPM 的 `new_page` 已经把 `data_` memset 成 0，但"0"在 free 链语义里表示"指向 page 0（即文件头）"，是错的；必须显式赋 -1。

> **Q2.1：为什么不让 BPM::new_page 顺手初始化 page_hdr？**
> A：BPM 是"通用块管理器"，不知道上层的 page format。让 BPM 不感知 RmPageHdr 的存在，将来其他模块（B+ tree、log）使用同一个 BPM 时不会被特殊化的初始化逻辑污染。这是分层设计的纪律。

### 2.1.9 `create_page_handle`（辅助）

```cpp
if (file_hdr_.first_free_page_no == RM_NO_PAGE) return create_new_page_handle();
return fetch_page_handle(file_hdr_.first_free_page_no);
```

短到三行，但是是 insert_record 复杂度的"心脏"。命中链头 → O(1) fetch；链空 → O(1) new_page。整体 insert 平均 O(1)。

### 2.1.10 `release_page_handle`（辅助）

```cpp
h.page_hdr->next_free_page_no = file_hdr_.first_free_page_no;
file_hdr_.first_free_page_no  = h.page->get_page_id().page_no;
```

头插入。两行但要保持顺序：先把当前页的 next 指向旧链头，再把链头切到当前页号。反过来写会先丢失旧链头指针。

> **Q2.2：为什么 `release_page_handle` 不需要校验"该页确实从满变未满"？**
> A：调用现场（`delete_record`）已经用 `was_full` 控制了，这里只是机械的"挂链"操作；分层化后 `release_page_handle` 的语义是"把一个当前未满且未在链上的页挂回链头"，不再做语义校验，让职责清晰。

> **Q2.3：fetch_page_handle 返回的 RmPageHandle 是按值返回的，里面的指针不会被复制构造破坏吗？**
> A：`RmPageHandle` 没有自定义拷贝/析构，按值返回时就是浅拷贝四个指针 + 一个引用——它们都指向 `page->data_`，只要 page 还 pinned 在缓冲池，就保持有效。这就是为什么 fetch_page_handle 的注释强调"pin the page, remember to unpin it outside"——`page` 的生命周期由 buffer pool 的 pin/unpin 决定，handle 本身只是个值类型视图。

## 3. 任务 2.2 · RmScan（顺序扫描游标）

### 3.1 状态机

`RmScan` 内部只有一个 `Rid rid_`，约定：

| `rid_` 取值 | 含义 |
|---|---|
| `(p, s)` 且 `p ∈ [1, num_pages)` 且 `bitmap[p][s] == 1` | 当前游标位置 |
| `(RM_NO_PAGE, -1)` | end 状态，扫描完成 |

公开 API 三个：
- 构造：从 `(1, -1)` 起步，调用 `next()`。
- `next()`：把游标推进到下一条有效记录。
- `is_end()`：`rid_.page_no == RM_NO_PAGE`。
- `rid()`：返回当前 `rid_`。

### 3.2 `next()` 算法

```text
若已 is_end，直接返回；
对当前 rid_.page_no 起始的每一页 p（直到 num_pages）：
    起始 slot = (p == 当前页) ? rid_.slot_no : -1
    fetch_page_handle(p)
    next_slot = Bitmap::next_bit(true, bitmap, n_per_page, 起始 slot)
    unpin(p, false)
    若 next_slot < n_per_page：
        rid_ = (p, next_slot)；返回
    （否则页内无更多 → 进入下一页）
循环结束仍没找到 → rid_ = (RM_NO_PAGE, -1)
```

要点：
1. **第一次循环用 `rid_.slot_no` 作起点**（这样 next_bit 会从 slot_no+1 开始），后续页用 -1（从 0 开始）。
2. **每页都立刻 unpin(false)**：扫描整个表可能涉及成千上万页，不 unpin 会让缓冲池迅速被全部 pin 住，新插入会失败。
3. fetch 失败这里不会发生（page_no 都在 [1, num_pages)）。

### 3.3 测试是怎么验证的

`record_manager_test::SimpleTest` 里有个 `check_equal` 函数，每轮随机 insert/update/delete 后调用：

```cpp
size_t num_records = 0;
for (RmScan scan(file_handle); !scan.is_end(); scan.next()) {
    assert(mock.count(scan.rid()) > 0);              // 扫到的 rid 必须在 mock 中
    auto rec = file_handle->get_record(scan.rid(), ctx);
    assert(memcmp(rec->data, mock[scan.rid()], ...) == 0);  // 内容一致
    num_records++;
}
assert(num_records == mock.size());                  // 数量一致
```

这意味着 `RmScan` 既不能漏一条（数量），也不能错位（内容），还不能多一条（rid 必须在 mock 中）。三者中任何一个写错都会立刻挂掉。

> **Q3.1：你的 next() 每页都 fetch+unpin，对长扫描会不会很贵？**
> A：每页都走一次缓冲池 lookup（hash 表 O(1)）+ 一次 mutex；命中时不涉及磁盘 I/O，CPU 上是百纳秒级。对于"全表扫"这种本来就 I/O bound 的操作而言无关紧要。如果要优化也很简单：在 RmScan 内部缓存"当前页 handle"，next() 在页内继续找时不释放、跨页时再 unpin 旧页 fetch 新页。这是一个 ~10 行的本地优化，留作后续 Lab3 的尝试方向。

> **Q3.2：扫描期间如果有人对该表 insert/delete，会发生什么？**
> A：当前 `RmScan` 是 **non-stable iterator**：
> - 已 unpin 的页面有可能被 victim 出局，下一次 fetch 时读到磁盘上**最新**的内容（含新增的 1 位）；
> - 如果一次 next() 内部已经走过的 page，**这一轮**不会再回头看，新增记录可能被漏；
> - 即将访问的 page 在被 fetch 前如果有 insert 进来，会被读到。
>
> 一致性由上层（事务/锁）保证。在 Lab4 里 `RmScan` 通常会在 Repeatable Read 隔离级别下被 LockManager 套上 S 锁。

> **Q3.3：is_end 用 `RM_NO_PAGE`（-1）作哨兵，会不会和合法 page_no 冲突？**
> A：合法 record-data 页的 page_no 范围是 `[1, num_pages)`，0 是文件头页，-1 在所有合法范围之外，正好做哨兵。`RM_NO_PAGE` 在 `rm_defs.h` 里被显式定义为 -1，并在文件头 `first_free_page_no = RM_NO_PAGE` 和 `next_free_page_no = RM_NO_PAGE` 中复用同一个语义（"无下一项"），保持代码的一致性。

## 5. 现场答辩"必背速查表"

```
┌──────────────────────────────────────────────────────────────┐
│ 单页布局                                                       │
│   [LSN 4B][RmPageHdr 8B][bitmap N/8 B][slots N×record_size]   │
│   page_hdr 偏移 = 4 (Page::OFFSET_PAGE_HDR)                   │
├──────────────────────────────────────────────────────────────┤
│ free 链表                                                      │
│   头：file_hdr_.first_free_page_no                            │
│   后继：page_hdr->next_free_page_no                           │
│   尾哨兵：RM_NO_PAGE = -1                                     │
│   不变式：链表 ⇔ 未满页面集合                                  │
├──────────────────────────────────────────────────────────────┤
│ insert 五步                                                    │
│   ① create_page_handle 取/造未满页                            │
│   ② Bitmap::first_bit(false) 找空 slot                        │
│   ③ memcpy 写记录                                             │
│   ④ Bitmap::set + num_records++                               │
│   ⑤ 满了？把当前页（恰是链头）从链摘掉                          │
│   ⑥ unpin(true)                                                │
├──────────────────────────────────────────────────────────────┤
│ delete 三步                                                    │
│   ① was_full = (num_records == n_per_page)  // 必须先记！     │
│   ② Bitmap::reset + num_records--                             │
│   ③ was_full ? release_page_handle (头插回链)                 │
│   ④ unpin(true)                                                │
├──────────────────────────────────────────────────────────────┤
│ RmScan::next 循环                                              │
│   for page_no in [当前页, num_pages):                         │
│       start = (首次? rid_.slot_no : -1)                       │
│       fetch -> Bitmap::next_bit -> unpin(false)               │
│       命中? 更新 rid_, return                                 │
│   均未命中 -> rid_ = (RM_NO_PAGE, -1)                         │
├──────────────────────────────────────────────────────────────┤
│ unpin 时 is_dirty 速查                                         │
│   只读路径 (get / scan)         : false                       │
│   写路径 (insert/update/delete) : true                        │
│   错抛异常之前的清理 unpin       : false                      │
└──────────────────────────────────────────────────────────────┘
```

## 6. 编码规约小结（可拿来对比代码）

1. **fetch / unpin 一一配对**：每条路径，包括异常路径，都要保证 fetch 出来的 page 最终被 unpin。RAII 包装是更优雅的做法（写一个 `ScopedPageHandle` 用 dtor unpin），但教学项目保持手写以使流程清晰。
2. **在调用 BPM 的方法前，先把所有"会修改 file_hdr 的操作"算清楚**：例如 `create_new_page_handle` 里 `num_pages++` 与 `first_free_page_no` 更新放在 buffer 写入之后，因为它们都不影响磁盘上的内容；`file_hdr_` 是内存里的 `RmFileHandle` 成员，由 `RmManager::close_file` 时统一刷回 `disk_manager_->write_page(fd, 0, &file_hdr_)`。
3. **bitmap / num_records / free 链 三者要保持一致**：删除/插入路径里这三处变更要么都做要么都不做，这是脏页的"事务边界"。
4. **不要绕过 `RmPageHandle`** 直接访问 `page->data_`：构造器已经把三段指针计算好，绕过它的字节偏移容易写错。
